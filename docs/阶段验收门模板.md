# 阶段验收门模板

本模板适用于 A–H 每个阶段的 Plan。Codex 在创建 `docs/plan/stage-<letter>.plan.md` 时复制“验收标准”章节；阶段分支 merge 到 main 后，在同一文件追加“验收状态”。不适用的验收门必须说明原因，不能留空。

## 验收标准

### 1. 范围与交付物

- [ ] 本阶段目标、非目标与 `AgenticPD-Demo审查与迭代计划.md` 一致；没有提前实现后续阶段能力。
- [ ] Plan 所列交付物均存在，目录职责、命名和语言规则符合 `AGENTS.md`。
- [ ] 变更范围已按相对 main 的 diff 审查；无无关重构、临时产物、密钥、绝对用户路径或未说明的兼容层。

### 2. 代码审查

- [ ] 已运行 `code-review`，并保存审查日期、范围和报告位置。
- [ ] P0、P1 问题均已由 Claude 最小范围修复并复审通过；P2 已记录，或明确获得延期处理的同意。

### 3. 零 LLM / 零 ORFS 验证

- [ ] 已运行 `code-test`；`make test`、数据模型自检和无副作用 CLI 契约检查均通过。
- [ ] 测试不依赖网络、LLM、OpenROAD、ORFS、PDK 或既有 `runs/`；失败回归用例已覆盖本阶段行为 bug。

### 4. 阶段专属自动验收

- [ ] 列出本阶段特有的自动验收命令、预期结果和证据路径。
- [ ] 核心新增或修改的契约具有正向与负向测试；例如数据模型状态、checkpoint 兼容/回退、失败分类、解析 fallback 或策略输入输出。

| 命令 | 预期结果 | 实际结果 / 证据 |
|---|---|---|
| `<command>` | `<expected>` | `<result>` |

### 5. 真实实验判定

Codex 必须在阶段收尾时选择且填写一项：

- [ ] **无需真实实验**：原因是改动只影响纯 Python 数据、文档、测试或已由 fixture 覆盖的逻辑；不得将此结论用于宣称真实 QoR 改善。
- [ ] **需要用户真实实验**：适用于改变 ORFS 命令/adapter、checkpoint 恢复、报告解析、参数落地、执行后端、QoR comparator 或任何可能影响真实 QoR/运行成本的改动。

若需要用户真实实验，必须在验收状态中写明以下内容，由用户执行后提供结果；Codex 复核证据后才能判定通过：

| 项目 | 必填内容 |
|---|---|
| 原因 | 哪项真实行为无法由零 ORFS 测试证明 |
| 配置 | `configs/experiments/<name>.yaml`、design/platform、seed、预算与环境 manifest |
| 命令 | 不含密钥且可直接复制的命令 |
| 预期证据 | ORFS 报告、trial/artifact、退出码、耗时、manifest 与关键日志路径 |
| 通过标准 | 可观察、预先固定的功能或 QoR 判据；不能事后调整 |

### 6. 准入结论

- [ ] 所有适用验收门通过；没有未处理 P0/P1；风险、P2 和真实实验结论已记录。
- [ ] 仅在以上条件满足后，允许 merge 到 main 并开始下一阶段。

## 验收状态

> 阶段分支 merge 到 main 后追加本节，不修改上方原始验收标准。

- **验收日期**：`YYYY-MM-DD`
- **审查范围**：`agenticpd-stage-<letter>` 相对 main 的变更
- **验证结果**：填写 code-review、code-test 与阶段专属命令的结果和证据路径。
- **真实实验判定**：填写“无需真实实验”或“需要用户真实实验”；后者附用户实际结果与 Codex 复核结论。
- **遗留风险 / P2**：无则写“无”。
- **merge commit**：`<commit>`
- **最终结论**：通过并可进入阶段 `<next>` / 未通过，原因：`<reason>`。
