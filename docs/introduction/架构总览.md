# 架构总览

## 1. 项目定位

AgenticPD 是运行在 ORFS 之上的物理设计 QoR 优化实验平台。它把一次候选配置的生成、执行、证据保存和 QoR 比较组织为可复现的 trial。平台的核心原则是：参数建议与执行分离，最终评价来自 ORFS finish 报告，checkpoint 复用必须经过兼容性和 manifest 校验。

项目同时保留两条运行路径：

- `main.py` 启动通用 AgenticPD 优化循环，支持真实或 mock LLM、真实或 mock ORFS、baseline、parse-only 与 resume。
- `tools/checkpoint_fork_verify.py` 启动独立的 checkpoint fork 验证实验，用 YAML 固定两个对照动作并生成独立报告。

两条路径共享配置、ORFS adapter、QoR 解析器、trial schema 与 manager，但后者不是前者的普通迭代模式。

## 2. 目录与职责

| 目录或文件 | 职责 |
|---|---|
| `main.py` | CLI 入口、session 创建、运行模式选择与日志初始化 |
| `config.py` | 路径、参数空间、默认运行配置、ORFS artifact 路径推导 |
| `optimizer.py` | 通用搜索循环、树/历史维护、trial 生命周期编排 |
| `agents/` | Judge/Stage Agent、观测摘要、真实与 mock LLM 客户端 |
| `search/tree.py` | 优化树的节点、分支关系、持久化与可视化输入 |
| `orfs/` | Make 命令、执行后端、阶段执行、日志脱敏、QoR 与失败解析 |
| `core/`、`storage/` | trial/checkpoint 数据模型、JSONL 索引、单 trial 文件、manifest 校验、决策痕迹 |
| `gwtw/` | Doomed/GWTW 统一编排：population、cohort、调度、裁决、恢复 |
| `configs/experiments/` | 可审阅的独立实验声明 |
| `tools/` | checkpoint 验证、trial 查看/复现、清理、树可视化 |
| `tests/`、`tests/fixtures/` | 零 LLM、零 ORFS、零网络的 Python 回归测试与只读证据 |
| `runs/` | session、trial、日志和报告的临时运行产物，不是唯一长期证据 |

## 3. 六个系统

### 3.1 运行与配置系统

`main.py` 解析 CLI 后，由 `FrameworkConfig` 汇总默认值与显式覆盖项。运行目录按 `runs/<platform>_<design>/<序号_时间戳>/` 创建，并写入 `config_snapshot.json`。配置系统还定义参数的类型、范围、交付方式和 `affects` 阶段，为 Agent 校验、ORFS 命令生成和 checkpoint 兼容性提供同一来源。

### 3.2 智能搜索与决策系统

`Optimizer` 维护优化树和历史。Judge Agent 根据历史生成分支节点、起始阶段和提示；Stage Agent 为需要重跑的阶段提出参数。`agents/llm.py` 提供真实客户端与 deterministic mock，便于将“策略问题”与“执行问题”分开验证。

当前搜索树是通用 AgenticPD 路径的导航结构；它不等同于 checkpoint manifest。树描述搜索关系，manifest 证明 artifact 是否可安全复用。

### 3.3 Trial 与 checkpoint 证据系统

`core/models.py` 定义 `TrialRecord`、`StageResult`、`CheckpointRef` 与失败分类。`TrialManager` 在 trial 开始、阶段完成和结束时更新 `trial.json`，并向 `trials.jsonl` 追加索引。`CheckpointManager` 构建 SHA-256 manifest、验证 artifact 完整性，并用参数的 `affects` 集判断 checkpoint 是否兼容。

该系统的关键关系如下：

```text
TrialRecord
 ├─ StageResult[]：命令、退出码、耗时、日志、阶段 QoR、失败信息
 ├─ final_qor：finish 后的 WNS/TNS/Area/Power
 ├─ parent_trial_id / branch_stage / param_diff
 └─ CheckpointRef：来源阶段、参数 hash、artifact manifest
```

### 3.4 ORFS 执行与解析系统

`orfs/command.py` 把参数渲染为 `make` 命令与必要的 FastRoute Tcl；`orfs/backend.py` 通过 `LocalBackend` 启动并超时终止进程组；`orfs/runner.py` 执行单阶段或全流程、生成 `StageResult`、清理下游 artifact 并脱敏日志；`orfs/parser.py` 读取 `6_report.json` 和兼容性 fallback。

`orfs/interface.py` 将这些部件编排为 `ORFSRunner`。`MockORFSRunner` 只用于隔离测试和无 EDA 调试，不能替代真实 QoR 证据。`SlurmBackend` 已定义接口，但当前仍是不可执行的 stub。

### 3.5 实验验证与回归系统

独立实验由 YAML 声明，`checkpoint_fork_verify.py` 依次执行 baseline、full restart 与兼容 checkpoint fork，并把接受条件、QoR、耗时、checkpoint 证据和 trial 索引写入 session。它使用正、负对照验证：不兼容变更必须被拒绝，兼容变更必须与 full restart 一致且节省时间。

`Makefile` 的 `make test` 只运行 Python 单元测试；它不启动 LLM、ORFS、网络或 PDK。fixture 用于锁定 QoR 解析、失败记录、manifest 和 schema 行为。

### 3.6 运维与观察系统

`trial_inspect.py` 查看 session 和 trial；`trial_reproduce.py` 用持久化参数重跑候选；`clean.py` 在明确 design 范围和确认后清理产物；`visualize.py` 从优化树生成图。它们是辅助工具，不应绕过 `TrialManager`、执行契约或清理范围限制。

## 4. 通用优化调度

通用路径的调度为单机同步循环：

```text
CLI / FrameworkConfig
        ↓
创建 session 与 baseline trial
        ↓
Judge 选择树节点和起始阶段
        ↓
Stage Agent 生成受限参数
        ↓
ORFSRunner 复制父产物并执行下游阶段
        ↓
Parser 读取 QoR，TrialManager 持久化证据
        ↓
Optimizer 更新历史、优化树与当前最佳候选
```

执行后端负责命令生命周期，不负责搜索策略。当前 `LocalBackend` 在调用线程中等待 `make` 完成；超时会终止整个子进程组。并发队列、资源调度和 Slurm 提交尚未进入运行时闭环，因此不能把当前实现描述为分布式调度器。

checkpoint fork 验证采用更严格的专用调度：先执行 baseline 并在 CTS 创建 checkpoint，再对每个动作先做兼容性判断；full restart 始终作为参考运行，只有兼容动作才执行 fork。该顺序避免把不兼容的 artifact 复用误判为正常优化结果。

## 5. 数据流

```text
配置 / YAML / CLI
        ↓
FrameworkConfig + 参数字典
        ↓
Action 或实验动作 ─────→ 参数校验与 checkpoint 兼容性判断
        ↓                              ↓
TrialRecord ← StageResult ← ORFS 命令与原始日志/报告
        ↓                              ↓
trial.json + trials.jsonl      6_report.json / artifact manifest
        ↓                              ↓
Optimizer 历史与树 / 实验 report.json ← QoR parser
```

数据分为三类：

- **配置数据**：`config.py`、CLI 覆盖、YAML、snapshot；决定一次运行的输入。
- **执行证据**：ORFS logs/reports/results/objects、命令、退出码、时间、manifest；用于复现与审计。
- **派生决策数据**：stage QoR、final QoR、优化树、历史、实验 verdict；必须能回溯到前两类数据。

绝对用户路径不得进入持久化 trial、实验报告或 session 日志；所有可保存路径应相对 session、flow 或项目根表达。

## 6. 已实现边界与后续接口

当前平台已具备 AgenticPD 搜索、ORFS 本地执行、结构化 trial、checkpoint manifest 和 checkpoint fork 对照验证。以下模块仍是架构预留或路线图内容：Slurm 实际提交、Pareto archive、GWTW population scheduler、Doomed Runs 特征/模型/反事实审计。

后续实现这些能力时，应通过新策略、scheduler 或 feature/model 边界接入，不应把职责继续堆入 `main.py`、Agent prompt 或 ORFS adapter。
