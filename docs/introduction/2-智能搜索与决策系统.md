# 2-智能搜索与决策系统

## 目标

这一层的任务不是直接“让 LLM 操作 OpenROAD”，而是把搜索问题拆成受约束的建议：从哪里分支、哪些下游阶段需要重跑、每个阶段哪些参数可改。真正的 shell 命令和 Tcl 由 ORFS adapter 负责。

这种分离很重要：LLM 的输出可能不合理，但它不能越过参数范围、阶段边界或 checkpoint 校验直接破坏执行流程。

## 决策对象

一次候选可以概括为：

```text
父节点 + 起始阶段 + 下游参数变更 → 一个新的 Trial
```

物理设计阶段按 `FP → PL → CTS → RT → finish` 前进。若从 PL 开始重新探索，FP 参数从父路径继承，只为 PL、CTS、RT 生成新参数，并只重跑这些下游工作；finish 用来取得最终 QoR。

当前实现把搜索关系记录为优化树，而把可复用的文件证据记录为 checkpoint manifest。两者相关但不能混为一谈：树说明“这个候选来自哪个候选”，manifest 证明“这些上游文件是否还能安全使用”。

## Judge 与 Stage Agent

`agents.py` 中有两类 Agent。

| 角色 | 输入 | 输出 | 不能做什么 |
|---|---|---|---|
| `JudgeAgent` | 优化树、最近历史、观测摘要 | 分支节点、建议起始阶段、搜索提示 | 不能直接给 make 命令或绕过阶段顺序 |
| `StageAgent` | 当前阶段、继承参数、Judge 提示、历史 | 本阶段合法参数和理由 | 不能修改其他阶段的变量 |

FP、PL、CTS、RT 各有一个具体的 Stage Agent。它们共享同一套输出校验：变量名必须属于该阶段，数值会转成声明类型并夹在 `ParamSpec` 的上下界内；无法获得有效输出时使用受限的 fallback，而不是把未经验证的文本送给 ORFS。

真实 `LLMClient` 使用 OpenAI 兼容 JSON 对话接口，遇到网络、限流或 JSON 解析问题会重试。`MockLLMClient` 返回确定性决定，适合把 API 不确定性从 Python 调度测试中剥离。两者都应输出结构化 JSON，而非自由文本。

## 优化树与历史

`optimization_tree.py` 提供有根树：根节点代表尚未对任何阶段做出选择；每条路径依次经过 FP、PL、CTS、RT 节点。节点保存所属阶段、父子关系、参数、QoR 摘要和被分支次数。

Judge 只从可分支节点中选择。已经到 RT 的叶节点没有下游阶段，不能再分支；同一节点也受 `max_branch_count` 限制，避免所有尝试都集中在一个局部选择上。

`Optimizer` 同时维护 Trial 历史。观测函数会从历史和树中提取：最近候选、当前最佳 QoR、各阶段的时序瓶颈、节点的探索均衡程度。这里的中间 stage 指标只帮助决定下一步，不是宣布获胜的依据。

```text
baseline
  ↓
观察历史与树
  ↓
Judge 选择一个可分支位置
  ↓
下游 Stage Agent 产生受限参数
  ↓
执行、解析、记录 Trial
  ↓
更新历史、树和当前最佳候选
```

## 验证边界

从 LLM 到真实执行之间至少有四道边界：

1. Agent 的 JSON 必须通过解析；
2. 参数必须属于当前阶段，并通过类型、范围校验；
3. 从父 trial 继承的 checkpoint 必须通过完整性和兼容性检查；
4. ORFS 完成后必须有完整的 finish QoR，候选才可参加最终比较。

最终比较由 `utils.qor_is_better()` 完成，规则是时序优先：先 WNS，再 TNS；只有在容差内才比较功耗和面积。它不是让 LLM 主观判断“看起来更好”。详见[实验契约](实验契约.md)。

## 约束与风险

- 搜索树不是全局最优证明，只是当前同步、单机搜索的导航记录。
- mock LLM 与 mock ORFS 只能验证控制流，不能说明策略对真实设计有效。
- 当前没有运行时 Pareto archive、GWTW population scheduler、Doomed Runs predictor 或跨设计学习模型；不能把规划中的能力当作现有功能。
- `SETUP_SLACK_MARGIN` 虽归 CTS Agent 管理，实际会影响更早的流程位置；其 `affects` 声明优先于“所属阶段”这个便于理解的分类。
