# 5-实验验证与回归系统

## 目标

实验验证要回答“这个结论是否可信”，回归测试要回答“这次改动是否破坏既有契约”。二者不能互相替代：真实 ORFS 运行证明物理设计行为，纯 Python 测试快速锁定数据模型、解析和安全边界。

## 实验声明

`configs/experiments/` 下的 YAML 是独立实验的声明。它应在运行前固定设计角色、参数空间、evaluator、预算、seed 和验收条件，而不是跑完后再补写一个看起来合理的说明。

现有 `smoke.yaml` 声明了 smoke/development/held-out 设计角色、环境版本记录、预算、当前九个参数的范围与基线、QoR evaluator 以及 smoke 验收条件。`stage-c-checkpoint-fork.yaml` 是专用 checkpoint fork 对照实验声明。

YAML 声明的是实验契约，不会自动使任何结果成立。真实执行后仍要保存 session、trial、ORFS 报告和验收结论。

## 对照设计

checkpoint fork 的正确性不能只做一次“fork 跑通了”的演示。专用工具 `tools/checkpoint_fork_verify.py` 使用 YAML 声明的动作，要求至少区分：

| 对照 | 要证明什么 |
|---|---|
| baseline | 作为共同起点，能完成并产生 checkpoint |
| 不兼容参数的阴性对照 | 系统必须拒绝不安全的 checkpoint 复用 |
| full restart | 相同候选从头执行，作为 QoR 参考 |
| 兼容 checkpoint fork | 可复用上游产物，并与 full restart 比较 QoR 和耗时 |

只有 manifest 验证通过、兼容性判断正确、fork 与 full restart 的 QoR 满足预先声明的容差，且耗时证据完整时，才能称 checkpoint fork 的这一实验通过。

## 验收证据

一次真实实验至少应能回溯到以下证据：

- 对应的实验 YAML 与 `config_snapshot.json`；
- platform、design、预算、seed 和环境版本信息；
- 每个 trial 的完整参数、状态、耗时、命令和相对日志/报告路径；
- ORFS finish 后的 `6_report.json`，或明确标注为兼容性 fallback 的来源；
- QoR comparator 的版本和容差；
- baseline、失败/超时 trial 与对照 trial，而非只留下最佳结果；
- 验收命令、结果和遗留风险。

`runs/` 是工作产物，不能成为唯一实验记录。特别是后续清理前，应确保需要长期保存的 YAML、报告摘要和验收记录已按项目流程归档。

## 纯 Python 回归

本项目的最低回归命令是：

```bash
make test
```

它调用 `python3 -m unittest discover -s tests -v`，约束是零 LLM、零 ORFS、零网络。测试关注 QoR 解析和比较、Trial schema 的序列化/不变量、checkpoint manifest 与兼容性，以及 fixture 的只读性。

这类测试很适合在实现前后频繁运行，但不能证明某个 PDK、OpenROAD 版本或真实设计一定可收敛。真实 smoke run 只能作为额外证据，不能被 mock 或单元测试替代。

## 约束与风险

- 参数空间、QoR comparator 或 ORFS 命令语义一旦变更，应先获授权并更新[实验契约](实验契约.md)，再开始可比较的新实验。
- 不同环境或未记录 revision 的运行不能轻易横向排名；`environment_manifest.json` 缺失信息必须诚实说明。
- 失败、超时和被拒绝的 fork 都会消耗预算，不能从统计中删除。
- 论文级结论至少需要冻结的 held-out 设计与预先定义预算；当前 smoke 配置明确不用于论文结论。
