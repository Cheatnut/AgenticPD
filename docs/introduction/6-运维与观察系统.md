# 6-运维与观察系统

## 目标

运维工具不负责产生优化决策；它们帮助人查看、复现、清理和理解已经产生的证据。正确使用这些工具的前提是：先明确目标 session、trial、platform 和 design，不能对宽泛目录做猜测式操作。

## Trial 查看与复现

`tools/trial_inspect.py` 用于列出 session、定位 trial，或显示 trial 的完整摘要和阶段结果。它读取 `TrialManager` 管理的记录，适合回答：某个候选改了哪些参数、在哪一阶段失败、最终 QoR 是什么、耗时多少。

`tools/trial_reproduce.py` 读取成功 Trial 的完整参数，以新的 variant 重新调用 ORFS，并打印原记录与新运行的 QoR 差异。它验证的是“在当前环境重新执行后是否一致”，不是从旧 JSON 中重新计算一个结果。

复现前应意识到三点：它会花费真实 EDA 时间；环境、工具版本或输入变动可能导致不同结果；复现 variant 不应覆盖原 trial 的证据。

## 清理机制

`tools/clean.py` 面向指定的 `<platform> <design>` 收集目标，默认先显示拟删除目录和大小；`--dry-run` 只预览，`--yes` 跳过交互确认。它会扫描 ORFS 的四类 variant 产物与该设计的 AgenticPD session。

工具显式禁止通配符，并保护名为 `base` 的基线 variant。即使如此，清理仍是不可逆操作：运行前必须核对 platform/design 和预览清单。项目规范要求清理时显式指定目标，不能采用宽泛递归删除。

`main.py` 的启动清理与 `clean.py` 的人工清理用途不同：前者只移除当前设计下陈旧的 `agenticpd_iter*` variant，防止实验污染；后者清理指定设计的多类运行产物。二者都不应被用来删除实验尚未归档的唯一证据。

## 可视化

`tools/visualize.py` 从 session 的优化树和 Trial 历史组织出图，帮助观察分支从哪个阶段开始、哪些路径通向当前较优结果。图表达的是搜索过程，不是物理版图，也不是 checkpoint 完整性的证明。

通用优化运行结束后，`main.py` 会尝试自动生成优化树图；生成失败只记录警告，不会把已完成的优化结果改为失败。应回到 `tree.json`、`trials.jsonl` 和 ORFS 报告确认事实，而不是只依据图片判断。

## 操作边界

| 工具 | 可安全回答的问题 | 不应替代的证据 |
|---|---|---|
| `trial_inspect.py` | 记录了什么、执行到哪里、参数是什么 | ORFS 的原始最终 QoR 来源 |
| `trial_reproduce.py` | 当前环境下能否按记录重跑 | 原 trial 的不可变历史 |
| `visualize.py` | 搜索路径和树形关系 | checkpoint manifest 或 QoR 比较 |
| `clean.py --dry-run` | 将会清理哪些目录 | 实际清理已执行的证明 |

所有工具都应通过配置或参数推导路径；输出中不应泄露 `.env`、token、绝对用户目录或完整敏感请求信息。

## 约束与风险

- `SlurmBackend` 尚未是可用运维通道，不能把 CLI 当作集群作业管理器。
- `agenticpd_best` 是导出的最佳候选副本，但“最佳”的判断仍依赖当次冻结的 comparator、容差和证据；跨实验不能只按目录名比较。
- 图、控制台摘要和 mock 结果是观察辅助，最终审计应回到结构化 Trial 和 ORFS finish 报告。
- 删除、覆盖 `.env`、修改 CI/CD 或向远端推送属于红线操作，需取得明确授权。
