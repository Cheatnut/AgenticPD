# 1-运行与配置系统

## 目标

这一层回答三个最基础的问题：**跑哪个设计、用什么参数跑、这次运行的证据放在哪里**。它不负责决定参数好不好，也不直接理解 QoR；它只把一次命令行请求变成一份固定、可追溯的运行配置。

可以把一次运行理解为一次实验。即使两次都优化 `gcd`，它们也必须各自有独立的 session 目录，避免日志、参数和 trial 相互覆盖。

## 先认识两层目录

- `flow/` 是 ORFS 的工作根目录。`make` 在这里运行，真实的 `results/`、`logs/`、`reports/`、`objects/` 也在这里。
- `flow/agenticpd/` 是本项目的 Python 控制层。这里的 `runs/` 保存每次 AgenticPD session 的元数据、配置快照、Trial 记录和框架日志。

因此，`runs/` 不是 ORFS 产物的替代品；它记录“为什么、如何运行”，ORFS 的报告记录“工具实际跑出了什么”。

## 入口

入口是 `main.py`。应从 `flow/` 目录运行，例如：

```bash
python3 agenticpd/main.py --baseline-only --design gcd
```

程序按下面的顺序工作：

```text
命令行参数
  ↓
读取 .env 到进程环境（只读取，不写入日志）
  ↓
确定 platform、design 与本次 session 目录
  ↓
构造 FrameworkConfig，并写入 config_snapshot.json
  ↓
选择运行模式和 Runner
  ↓
交给 Optimizer 或仅解析已有 QoR
```

常用模式的含义如下。

| 命令选项 | 做什么 | 是否调用 LLM | 是否启动 ORFS |
|---|---|---:|---:|
| `--baseline-only` | 仅执行基线 trial，用于先验证真实流程 | 否 | 是，除非同时使用 mock ORFS |
| `--iterations N` | 基线后再做 N 次搜索迭代 | 是，除非 `--mock-llm` | 是，除非 `--mock-orfs` |
| `--mock-llm` | 用确定性的假 LLM 代替 API，验证调度逻辑 | 否 | 取决于是否使用 `--mock-orfs` |
| `--mock-orfs` | 生成合成 QoR，验证 Python 控制流 | 取决于 LLM 选项 | 否 |
| `--parse-only VARIANT` | 只读取已有 variant 的报告 | 否 | 否 |
| `--resume [目录]` | 继续既有 session；不写该 session 的新目录 | 取决于其他选项 | 取决于其他选项 |

`--mock-orfs` 的数字没有物理意义，不能作为任何 QoR 结论或验收证据。

## 配置对象

`config.py` 是配置的单一来源，核心对象是 `FrameworkConfig`。它保存目标平台和设计、超时、迭代次数、LLM 设置、QoR 容差，以及所有路径推导方法。

配置优先级很简单：`FrameworkConfig` 的默认值最低；命令行中**显式提供**的参数覆盖默认值。未传的命令行选项不会意外改动默认值。

例如，`--timeout 7200` 只覆盖单次流程超时；平台、设计和 QoR 容差仍使用其余默认配置。构造完成后，完整配置会写入 session 内的 `config_snapshot.json`，这是日后复现实验的输入快照。

### 参数空间是什么

`PARAM_SPACE` 把可调变量声明为 `ParamSpec`。每个变量包含：名称、所属阶段、数值类型、允许范围、基线默认值、交付给 ORFS 的方式，以及它实际会影响哪些阶段。

当前共有九个变量，按四个物理设计阶段组织：

| 阶段 | 初学者理解 | 当前变量 |
|---|---|---|
| FP | 决定芯片大致形状和可用面积 | `CORE_UTILIZATION`、`CORE_ASPECT_RATIO` |
| PL | 决定标准单元怎样摆放 | `PLACE_DENSITY_LB_ADDON`、`CELL_PAD_IN_SITES_GLOBAL_PLACEMENT` |
| CTS | 构建时钟树 | `CTS_CLUSTER_SIZE`、`CTS_CLUSTER_DIAMETER`、`SETUP_SLACK_MARGIN` |
| RT | 完成全局路由和详细路由前的关键设置 | `FASTROUTE_LAYER_ADJUSTMENT`、`GRT_CONGESTION_ITERATIONS` |

`BASELINE_PARAMS` 不是“所有变量都取零”，而是尽量保持 ORFS 原始 flow 的行为。某些变量在“不传入”和“传入 0”时语义不同，例如 `PLACE_DENSITY_LB_ADDON`；因此基线会保留为空，让 ORFS 使用其自身默认值。

### `affects` 为什么重要

每个变量还声明 `affects`。它表示“改动这个变量后，哪些已经完成的阶段产物不再可信”。例如 `GRT_CONGESTION_ITERATIONS` 只影响 RT，所以 CTS checkpoint 可以继续使用；而 `CORE_UTILIZATION` 会影响从 FP 到 RT 的所有阶段，不能复用 CTS checkpoint。这个字段同时供参数校验、checkpoint 兼容性判断和实验审计使用。

## Session 生命周期

新 session 的目录形如：

```text
runs/sky130hd_gcd/001_20260729_143000/
├── config_snapshot.json
├── agenticpd.log
├── tree.json
├── trials.jsonl
└── iter-0-<trial_id>/
    └── trial.json
```

其中 `001_` 是同一 platform/design 下递增的序号，时间戳降低人工查找成本。每次新的普通运行创建新 session；`--resume latest` 选择该设计最近的 session，显式目录则选择指定 session。

程序启动后还会清除旧的 `agenticpd_iter*` ORFS variant，以免旧迭代残留让 `make` 错把某阶段当作已完成。共享基线 `agenticpd_baseline` 和导出的最佳结果 `agenticpd_best` 不在此范围内。清理属于有副作用的操作，使用真实流程前应确认目标 platform/design 正确。

## 输入与输出

一次通用运行的输入是：命令行覆盖、`config.py` 的参数空间与默认值、设计的 ORFS `config.mk`，以及真实模式下的 LLM 环境变量。`.env` 只用于向当前进程提供密钥，不能进入 Trial、日志或提交记录。

输出分为三层：

- session 层：配置快照、框架日志、优化树、JSONL 索引；
- trial 层：每个候选的 `trial.json`，保存参数、阶段结果、最终 QoR 和谱系；
- ORFS 层：`flow/results/`、`logs/`、`reports/`、`objects/` 下的 variant 产物和最终报告。

路径均由项目位置、`FrameworkConfig` 或参数推导，不能把某个用户目录写死在代码或持久化记录中。

## 约束与风险

- 当前参数范围主要针对 `sky130hd/gcd`。换设计时，不能假定范围仍然合理，应重新声明并验证实验参数空间。
- `--parse-only` 只能说明解析器能否读到已有报告，不会验证 ORFS 命令或 LLM 决策。
- `config_snapshot.json` 记录了本次 Python 配置，但不能单独替代 ORFS、PDK、OpenROAD 的版本信息；跨环境比较还应检查 `environment_manifest.json`。
- 真正的 API key 必须经环境变量提供；文档、配置快照、命令日志和 Trial 都不应保存密钥。
