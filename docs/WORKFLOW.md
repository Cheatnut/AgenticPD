# AgenticPD 多 Agent 协作流程

## 1. 目的与适用范围

本文档是 AgenticPD 中 Codex、Claude 与用户协作的唯一流程真相源。`AGENTS.md` 只规定 Codex 的角色边界，`CLAUDE.md` 只规定 Claude 的角色边界；功能目标和实现范围以用户确认的方案为准。若三者冲突，应先停止工作并由用户确认，不得自行选择有利解释。

协作目标不是增加 Agent 数量，而是通过职责分离、批量交付和独立证据，减少用户转述、重复审查及局部补丁链。

## 2. 角色与决策权

### 用户：范围与红线负责人

- 确认功能范围、重大架构取舍、实验口径和计划变更。
- 批准真实实验及删除、push、rebase、历史重写、密钥、CI/CD 等红线操作。
- 不负责判断实现是否正确，也不负责把技术问题拆成逐条修复任务。

### Codex：Planner / Checker

- 扫描现状，定义一次性交付包、验收行为、证据和非目标。
- 独立检查代码、断言、配置、路径安全、文档一致性和回归风险。
- 原则上只读，不替 Claude 实现；验收不得仅采用 Claude 的完成声明。
- 验收通过后负责获授权的 Git 收尾。

### Claude：Executor

- 按已确认的交付包实现代码、回归测试及获授权文档。
- 对相邻接口做必要回归，不只修改 Codex 点名的单行位置。
- 不擅自改变范围、实验契约或验收标准，不自行 commit、merge 或 push。

### 确定性证据

测试输出、Trial/Checkpoint/DecisionTrace、ORFS 原始报告和 Git diff 是证据；Agent 的文字总结不是证据本身。mock 结果不得替代真实 ORFS 结论。

## 3. 标准五步流程

### 第一步：确认验收合同

Codex 先给出一个完整交付包，至少包含：

- 目标与非目标；
- 涉及的接口和允许修改的范围；
- 必须证明的行为及反例；
- 可随仓库复现的纯 Python 验证命令（`make check`，本地 `tests/` 存在时附加 `make test`）；
- 是否需要真实实验及其准入条件。

重大范围或实验口径变化由用户确认后才进入实现。普通实现细节由 Claude 在合同内自行决定。

### 第二步：Claude 批量实现

Claude 一次完成当前交付包中的全部 P0/P1、行为回归测试和必要配置，不按单个函数反复往返。实现完成后提交交付报告，不得仅回复"已修复"。

### 第三步：Codex 独立验收

Codex 从系统数据流和失败路径反向检查，不按 Claude 报告的顺序照单确认。必须同时核对：

- 测试名称、断言与声称行为是否一致；
- mock/fake 是否掩盖真实接口问题；
- 持久化证据是否能证明实际执行；
- resume、预算、失败和边界输入；
- 无关改动、路径、语言及文档契约。

### 第四步：集中返工

Codex 一次性汇总所有 P0/P1，Claude 集中修复。原则上一个交付包只允许一次集中返工；若复审出现新 P0/P1，Codex 应说明上一轮为何未发现，Claude 应说明为何相邻回归未覆盖。P2 默认记录后置，不阻塞当前交付。

### 第五步：实验与 Git 收尾

纯 Python 门通过后，Codex 判断是否需要真实实验。需要时由用户执行或明确授权执行，并提供配置、命令、原始证据路径和通过标准。全部验收门通过后才能形成验收记录、commit 和 merge；push 必须另行取得用户明确授权。

## 4. 一次性交付包与完成定义

每个交付包应覆盖一个可独立验收的闭环，而不是一个函数或一个测试。满足以下条件才算完成：

- 目标行为已实现，非目标未被顺带引入；
- 行为 bug 在本地 `tests/` 中有先失败后通过的回归测试，并在交付报告中记录测试名称与关键断言；
- 测试断言直接证明目标行为，而非只证明字段存在或命令未报错；
- `make check` 和交付要求的所有自检通过；本地 `tests/` 存在时，`make test` 也必须通过；
- P0/P1 遗留为零，P2 已明确记录；
- 若交付要求真实实验，原始结果已通过验收。

测试数量增加不是完成证据；关键在于断言能否区分正确实现和错误实现。

## 5. 交付与审查格式

Claude 的交付报告固定为两部分，使用连续编号，不用表格：

1. **给你**：改动范围、行为结果、是否影响真实 ORFS/checkpoint/QoR。
2. **给 Codex**：逐条回应验收合同，列出测试名称与关键断言、完整验证结果、P0/P1/P2 遗留和证据路径。

Codex 的审查报告固定为：

1. **给你**：通过门、未通过门、证据、影响和准入结论。
2. **给 Claude**：集中列出 P0/P1，格式为 `[位置] <问题> <请你……>`，并说明复修证据。
3. **需要你做**：只列真实实验、外部确认或红线授权；没有则写"无"。

用户转发时只需发送完整交付包或完整交付报告，不再逐条改写技术内容。

## 6. 停止条件

出现以下情况应停止当前步骤并请求用户决策：

- 方案缺失，或实现需要超出已确认范围；
- 需要修改参数空间、QoR comparator、ORFS 命令语义或实验契约；
- 需要执行任何红线操作；
- 证据相互冲突，无法通过只读检查判定；
- 同一交付包经过一次集中返工仍存在 P0/P1。

## 7. 用户最小操作清单

每个交付周期用户通常只需：

1. 确认 Codex 给出的范围与重要取舍；
2. 将一次性交付包原样交给 Claude；
3. 将 Claude 的完整交付报告原样交回 Codex；
4. 按需执行真实实验或批准红线操作；
5. 确认最终 merge/push。

用户无需自行审查代码，也无需在两个 Agent 之间解释技术结论。发生分歧时，由提出结论的一方提供文件位置、运行证据或最小反例。
